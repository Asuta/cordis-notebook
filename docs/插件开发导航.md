# 插件开发导航

这是所有应用共用的快速入口；应用自己的 `agent.md` 负责补充应用专属服务和示例。先确认当前应用 ID、工作区和 `git status`，再按任务选择最短阅读路径。

工作台 Agent 优先调用 `workspace_development_info`，按任务选 `ui`、`backend` 或 `agent`，一次获取本应用真实契约、服务、示例和验证方式。新增插件使用返回的模板调用 `workspace_scaffold_plugin`：工具先写齐并校验完整骨架，再整体发布到插件目录，避免开发服务器发现缺入口的清单。默认停用；仍需实现需求和补充相应验证。应用专属入口由 `applications/<app>/development.json` 维护。

已知模板时可传 `{ template: "notebook-footer" }`，专项任务可用返回的 tasks ID，例如笔记正文功能的 `{ task: "note-content" }`；task 和 template 二选一。入口默认只返回相关服务，`includeAllProviders: true` 显式展开本应用完整索引。通用 client/server 模板只带宿主契约；应用模板补充它依赖的契约与示例。脚手架的 `sources` 返回各文件完整源码与真实路径，可直接编辑；`files` 仍保留路径数组，不必再逐个读取。新增应用通过 development.json 的 recipes.services、templates.recipe 或 tasks.recipe 声明入口；不在工具中硬编码应用服务。

## 按任务选择入口

- 普通前端插件：先看本应用里最接近的 `plugins/*/package.json` 和 `client.js`，再看 [Workspace 插件开发指南](Workspace插件开发指南.md) 的清单、挂载、样式和验证章节。
- 需要界面扩展：使用清单里的 `requires.client` 声明服务，用 `sdk.mount(name, node)` 消费挂载点，用 `sdk.slot(name, target)` 提供挂载点；不要依赖其他插件的内部 DOM。
- 需要 React：阅读 UI 服务和同应用的 React 插件示例；共享 UI、主题和布局由提供者维护。
- 需要数据、配置或 Agent 工具：先找对应的服务契约和同应用示例，再决定是否需要后端插件。代码依赖写 `dependencies`，运行时服务依赖写 `cordis.requires`。
- 需要生命周期清理：使用 `ctx.effect`、`sdk.listen` 和挂载 API 登记定时器、监听器、DOM、订阅及请求的释放。

## 开发模式与验证

工作台管理的 Vite 开发模式会让运行源码、插件清单和运行依赖按需热更新；普通插件修改不需要 `workspace_build` 或 `workspace_restart`，用 `workspace_status` 确认 `development.events`。测试、类型测试、Markdown/README 等说明文件不属于运行图，修改它们不会卸载或重挂载插件。正式构建或宿主、公共协议改动需要按架构说明扩大验证。

普通插件优先运行 `workspace_test({ plugins: ["<插件 ID>"] })` 或 `pnpm test:plugin --app <应用 ID> --plugin <插件 ID>`。它会检查类型契约、构建目标应用并运行插件测试及已声明的关联回归；这不等于真实浏览器验收。报告必须分别说明类型检查范围、构建范围、实际测试文件和通过数、浏览器验收状态及剩余缺口。用户关闭浏览器验收时不得绕过开关。

修改源码前保留用户已有改动；不自动提交、推送或部署。新增 workspace 包或依赖后使用 `pnpm install`。

浏览器定位失败时先用返回的候选和页面结构确认唯一目标；用 `browser_report({})` 直接读取完整验收报告，结束后仍可读取。不要把工作台报告路径拼到独立业务应用端口；后续成功不能覆盖真实失败。验证通过且源码未变时不例行重跑，结束总结直接依据已有结果。

已确认目标的一组操作可用 `browser_batch({ steps: [...] })` 顺序执行，最多 12 步、总时限 60 秒；整批先校验参数，失败即停，返回 stoppedAt（从 1 开始）、失败现场和已执行结果。不能预先猜下一页目标；需要新结构时先到 snapshot，再提交下一批。各步和截图均写入报告，返回最后一张图片供检查。

代码修复后调用 `browser_retest({ reason: "修复内容" })`。工具先收集并关闭旧验收，再创建新的空数据实例与报告 ID，保留 previousAttempts、关联 ID、旧失败和截图；需重新准备测试数据，结束仍用 browser_finish。每轮最多 4 次复测，已通过或已取消的验收不能重开。工作台显示最新复测状态及各次历史报告；最终分别说明首次失败和复测覆盖，不能把最新通过说成此前从未失败。

开发入口的 `runtime` 同时返回业务实例地址、受管理实例的数据目录和插件启用协议。不要假定数据一定在 `root/data`：工作台可通过 `DATA_DIR` 隔离存储，外部实例的目录不作推断。`defaultEnabled` 仅影响首次登记，已经保存的开关优先。启用优先用插件管理界面；走 HTTP 时先读取业务实例 `/api/applications`，确认 `current.id` 和 `phase`，使用最新 `session` 作为 `x-application-session` 请求头调用 `/api/plugins/<id>/toggle`，再检查目标插件的 `enabled/state/error`。不直接改状态文件。独立浏览器验收的开关与数据不影响用户页面所在实例。
