# 插件开发导航

这是所有应用共用的快速入口；应用自己的 `agent.md` 负责补充应用专属服务和示例。先确认当前应用 ID、工作区和 `git status`，再按任务选择最短阅读路径。

工作台 Agent 先从本轮自动提供的开发路径目录选 task，首次 `workspace_development_info` 就传匹配的 task；没有匹配项时再选 focus（ui/backend/agent）、已知 template 或 capability，一次获取当前任务相关的全部契约、示例清单、实现正文和验证方式。新增插件使用返回的模板调用 `workspace_scaffold_plugin`：工具先写齐并校验完整骨架，再整体发布到插件目录，避免开发服务器发现缺入口的清单。默认停用；仍需实现需求和补充相应验证。应用专属入口由 `applications/<app>/development.json` 维护。

已知模板时可传 `{ template: "notebook-footer" }`，专项任务可用返回的 tasks ID，例如笔记正文功能的 `{ task: "note-content" }`；task 和 template 二选一。入口默认返回相关服务，并展开场景及其提供者声明的全部相关契约和示例正文（`includeRelatedSources` 默认 true），与完整资料方案一致。`capabilities` 是去重后的能力发现索引，`selectedCapabilities` 标记当前选择。`includeAllProviders: true` 仅展开本应用完整服务索引，不扩大源码范围；只有显式传 `includeRelatedSources: false` 才收窄为使用契约和单个示例，此时 `relatedSources` 列出省略路径，可用 `expandSources` 恢复完整资料。无场景契约的新能力仍可通过 `capability` 读取契约、示例和生命周期。通用 client/server 模板只带宿主契约；应用模板补充它依赖的契约与示例。脚手架的 `sources` 返回各文件完整源码与真实路径，可直接编辑；`files` 仍保留路径数组，不必再逐个读取。新增应用通过 development.json 的 recipes.services、templates.recipe 或 tasks.recipe 声明入口；不在工具中硬编码应用服务。

UI 任务还返回 `presentation.styles/icons/ordering`：优先用模板的资料，其次用该应用的 UI 资料；通用 client 模板只带通用说明。笔记页脚给出主题变量、可选 ui 图标与挂载顺序；画布动作给出局部变量的适用范围、菜单 order 示例与图标接口限制。`presentation.sources` 附真实文件的路径、行号和少量正文，每段最多 40 行、2500 字符；无需再扫描整份样式和图标实现。应用维护者在 development.json 的 presentation.references 中维护对应选段，功能和源码变动时一并更新。

## 按任务选择入口

Agent 启动时会从绑定应用的 `development.json` 自动生成任务和模板目录，直接加入本轮上下文；生成目录不扫描插件或读取示例源码，不增加模型或工具调用轮次。首次 `workspace_development_info` 优先传目录中匹配的 task，不必先读默认 UI 资料再寻找专项任务。没有匹配项时仍可用 focus 或 capability；组合需求可以分别读取必要路径。完整资料的默认展开行为不变。

路径按扩展方式复用，不为每个功能单独写教程。应用维护者在 tasks 中声明唯一 id、description（说明适用需求及边界）、focus 和 recipe；recipe.services 关联能力提供者，专属 examples 补充组合用法。服务契约、生命周期继续由提供者的 capabilities 维护。模板是可生成的骨架，任务是资料组合；不要把任务 id 传给脚手架。目录与工具返回使用同一份配置，无需同步维护第二张任务表。`test/development-navigation.test.js` 检查所有应用的路径文件、源码选段及服务引用。

笔记应用覆盖三条路径：`note-content` 用于正文读取及统计展示；`note-action` 用于现有笔记的按钮或菜单动作；`note-editor` 用于新格式或编辑器。灵感画布提供 `studio-action`（菜单动作）、`studio-card`（新卡片）、`studio-provider`（生成服务）、`studio-agent-action`（Agent 扩展操作）和 `studio-extension`（已有卡片及侧栏增强）五个模板；另有 `studio-provider-advanced`（HTTP、模型参数与恢复）和 `studio-settings`（可组合设置及私有持久化）两个任务配方，复用 provider 骨架。配套模板、测试和公共场景见 [画布开发路径](../applications/studio/development/README.md)。其他应用沿用自己的模板和 focus，无需在框架里增加应用名称分支。

- 普通前端插件：先使用开发入口的契约和消费示例；清单、挂载或验证仍有疑问时查阅 [Workspace 插件开发指南](Workspace插件开发指南.md) 的清单、挂载、样式和验证章节。
- 需要界面扩展：使用清单里的 `requires.client` 声明服务，用 `sdk.mount(name, node)` 消费挂载点，用 `sdk.slot(name, target)` 提供挂载点；不要依赖其他插件的内部 DOM。
- 需要 React：阅读 UI 服务和同应用的 React 插件示例；共享 UI、主题和布局由提供者维护。
- 需要数据、配置或 Agent 工具：先找对应的服务契约和同应用示例，再决定是否需要后端插件。代码依赖写 `dependencies`，运行时服务依赖写 `cordis.requires`。
- 需要生命周期清理：使用 `ctx.effect`、`sdk.listen` 和挂载 API 登记定时器、监听器、DOM、订阅及请求的释放。

## 开发模式与验证

工作台管理的 Vite 开发模式会让运行源码、插件清单和运行依赖按需热更新；普通插件修改不需要 `workspace_build` 或 `workspace_restart`，用 `workspace_status` 确认 `development.events`。测试、类型测试、Markdown/README 等说明文件不属于运行图，修改它们不会卸载或重挂载插件。正式构建或宿主、公共协议改动需要按架构说明扩大验证。

普通插件优先运行 `workspace_test({ plugins: ["<插件 ID>"] })` 或 `pnpm test:plugin --app <应用 ID> --plugin <插件 ID>`。它会检查类型契约、构建目标应用并运行插件测试及已声明的关联回归；这不等于真实浏览器验收。报告必须分别说明类型检查范围、构建范围、实际测试文件和通过数、浏览器验收状态及剩余缺口。用户关闭浏览器验收时不得绕过开关。

修改源码前保留用户已有改动；不自动提交、推送或部署。新增 workspace 包或依赖后使用 `pnpm install`。

浏览器定位失败时先用返回的候选和页面结构确认唯一目标；用 `browser_report({})` 直接读取完整验收报告，结束后仍可读取。不要把工作台报告路径拼到独立业务应用端口；后续成功不能覆盖真实失败。验证通过且源码未变时不例行重跑，结束总结直接依据已有结果。

已确认目标的一组操作可用 `browser_batch({ steps: [...] })` 顺序执行，最多 12 步、总时限 60 秒；整批先校验参数，失败即停，返回 stoppedAt（从 1 开始）、失败现场和已执行结果。不能预先猜下一页目标；需要新结构时先到 snapshot，再提交下一批。各步和截图均写入报告，返回最后一张图片供检查。

代码修复后调用 `browser_retest({ reason: "修复内容" })`。工具先收集并关闭旧验收，再创建新的空数据实例与报告 ID，保留 previousAttempts、关联 ID、旧失败和截图；需重新准备测试数据，结束仍用 browser_finish。每轮最多 4 次复测，已通过或已取消的验收不能重开。工作台显示最新复测状态及各次历史报告；最终分别说明首次失败和复测覆盖，不能把最新通过说成此前从未失败。

开发入口的 `runtime` 同时返回业务实例地址、受管理实例的数据目录和插件启用工具。不要假定数据一定在 `root/data`：工作台可通过 `DATA_DIR` 隔离存储，外部实例的目录不作推断。`defaultEnabled` 仅影响首次登记，已经保存的开关优先，不直接改状态文件。

启用优先调用 `workspace_enable_plugin({id:"<插件 ID>"})`。它核对受管理实例、绑定应用与最新 session，再启用或读取已启用插件的状态；有页面时复用插件管理流程、保存保护和单选组确认。返回 `enabled`（保存的启用选择）、`running`、`serverState/clientState`、`waitingFor/dependencies` 与 `error/operationError`。缺依赖或加载失败时 `running=false`；无页面的前端状态未知时 `running=null`，不能声称插件已运行。无页面不能发起单选组切换；工具不自动启用依赖，不盲目重放超时写入，页面验证后状态变化会重新读取并取消前端确认。

这些是运行状态检查，不能代替功能测试与本轮浏览器验收。独立浏览器验收的开关与数据不影响用户页面所在实例。手动 HTTP 的兼容协议仍在 runtime.activation 中：先读 `/api/applications`，确认应用与 phase，再使用最新 session 请求头调用 toggle，最后读实际状态；HTTP 成功不能证明前端已经加载。

验收先 `browser_open`，再用 `browser_plugin({id:"<插件 ID>"})` 查询独立实例状态；加 `enable:true` 启用并核对前后端。它复用宿主启用流程与保存保护，不共享工作台开关，不计为功能断言。通用前端和笔记页脚骨架的根节点带 `data-testid="plugin-<插件 ID>"`；使用 snapshot 返回的 targets 定位，笔记插件中心还提供 `plugin-select-<ID>` / `plugin-toggle-<ID>`。断言默认等待目标值最多 5000ms，可用 timeoutMs（0–10000）调整；仅最终检查写入报告，超时或重复匹配仍是真实失败。
