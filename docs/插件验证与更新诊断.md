# 插件验证与更新诊断

## 通用插件验证

在仓库根目录执行；`test:plugin` 适用于任意应用和插件：

```powershell
pnpm test:plugin --app notebook --plugin theme-teal
pnpm test:plugin --app notebook --plugin free-page-editor
pnpm test:plugin --app notebook --plugin editor --plugin editor-host --list
```

`--plugin` 可重复。`--list` 只读取清单、列出测试选择原因及覆盖缺口，不构建、不执行测试。正常执行依次进行全局类型检查、目标应用与通用宿主正式构建、所选测试；前一阶段失败即停止。当前应用内的运行时测试会扫描完整插件目录，因此构建整个目标应用，保证新插件也有 dist。验证不会重启正在运行的应用。

插件自己的测试放在 `applications/<app>/plugins/<id>/test/**/*.test.js`（也支持 `.test.mjs`、`.test.cjs`）。递归发现时忽略隐藏目录、node_modules 和 dist。不要把运行时测试放在源码入口中。测试可用 `CORDIS_TEST_APP` 和 JSON 格式的 `CORDIS_TEST_PLUGINS` 取得本次范围。

跨插件测试在 `test/coverage.json` 中明确声明应用以及覆盖的插件 ID 或服务。服务按前后端分别匹配所选插件的 requires/provides，不分析测试正文或猜测关联。示例：

```json
{
  "version": 1,
  "tests": [
    {
      "file": "test/documents.test.js",
      "application": "notebook",
      "plugins": ["export"],
      "services": { "client": ["documents"] }
    }
  ]
}
```

每次执行使用 `work/verification/<唯一ID>/` 下的独立数据和报告；端口环境变量为 0。测试仍须使用临时目录/独立端口，不硬编码用户数据路径，也不启动生产服务。报告保存阶段、耗时、退出码和末尾输出；命令输出实时显示。重跑生成新报告，不覆盖首次失败。报告可能为 `failed`、`passed` 或 `passed-with-gaps`。后者表示所选检查通过，但存在缺少插件内业务测试、未声明关联回归、需要真实浏览器验收等缺口；不能声称全部业务或视觉效果已经验证。

工作台 Agent 的 `workspace_test({plugins:["插件ID"]})` 调用同一入口，应用由当前对话绑定；它与命令工具共用运行会话，可继续读取或终止。正式构建后还会按运行时规则校验产物。普通插件改动默认定向验证；宿主、公共协议、全局依赖改动应扩大集成回归，必要时执行 `pnpm test` 全量验证（同时收集根目录和各插件内的测试），并解释范围。首次失败即使重跑通过，也须如实保留原因与证据。界面改动另用浏览器和独立测试数据验收。

## 热更新诊断

工作台的「热更新状态」显示每个页面的标识、阶段和已等待时间；超时或失败时自动展开。`workspace_status` 的 `development.saving` 与 `development.blocked` 提供同一信息，阶段为 `unresponsive`（尚未响应）、`queued`（排队中）、`saving`（正在执行保存保护）、`confirmed`（已确认）、`failed`（保存失败）。尚未响应不能推断为页面正在保存或被冻结。

准备进度携带本轮 token；进度消息不能代替保存确认，迟到确认不能放行新一轮更新。`unblocked` 仅表示等待解除、将重新校验和重试。收到插件更新/刷新或成功结果后才能报告更新完成。保存超时仍保留旧应用并释放编辑保护，不绕过尚未确认的页面。

对应用目录清单相同、插件清单及加载计划相同、没有待恢复失败入口的重复扫描，报告 `noop`，不请求页面保存、替换插件或增加版本。即使 targets 为空，应用改名、目录增删仍按正常流程处理。第一版保留现有等待页面范围。

## 状态文件写入

插件启停状态、插件配置、应用选择与工作台会话共用 `shared/persistence.js`：同一进程内同路径排队，每次使用唯一临时文件，再替换目标。EPERM/EACCES/EBUSY 在有限延迟后重试，持续失败保留旧文件并返回错误，不先删除目标或直接覆盖内容。

发生重试、恢复、最终失败或临时文件清理失败时，日志记录路径、PID、阶段、次数和耗时，不记录快照内容。这些诊断用于定位文件占用及写入重叠；重试成功不能证明原始故障原因。同进程队列不协调多个独立应用进程；不同实例仍应使用独立数据目录。

本次涉及工作台服务、Agent 工具定义与开发脚本，现有工作台需要重新启动后才能完整加载这些能力。只重启业务应用不会加载新的工作台工具。
