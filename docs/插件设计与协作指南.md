# 插件设计与协作指南

本文帮助插件作者做设计取舍：让插件容易理解、合作、替换和维护，同时保留实现上的自由。它是一份指导文档，不引入新的构建拦截、权限机制或运行时限制。

当前项目继续采用完全信任模式。已有的清单校验、依赖管理和生命周期机制保持原样；本文中的设计建议不应被解释成框架已经实施的强制规则，也不要求为例外额外建立审批流程。

具体开发步骤见 [Workspace 插件开发指南](Workspace插件开发指南.md)，服务接口见 [内置插件服务契约](内置插件服务契约.md)。当前仅保留 workspace 插件；第三方安装体系暂不设计。

应用间的插件目录与运行环境独立；本文的服务协作指同一应用内部。业务请求通过 `sdk.request()`，浏览器持久化通过 `sdk.storage.local/session`，后端私有数据通过 `runtime.dataDir`，使切换应用后仍能找到正确的数据。

## 1. 自包含允许合作

插件自包含，是让自己的实现、清单、类型、样式和资源有明确归属，让需要什么能力、提供什么能力可以被理解。它不要求插件完全独立运行，也不要求每个插件重复实现 React、存储或其他公共能力。

依赖另一个插件的公开服务是正常协作。判断耦合是否值得调整，可以问：对方保持公开接口不变，只改变内部实现，我的插件是否还需要跟着修改？如果需要，看看双方是否依赖了未明确约定的细节。

不是每个细节都需要抽象成新服务。只有一个消费者、双方明确共同演进的小功能，可以先保持简单；出现真实的第二种实现或重复需求时，再提炼接口。

## 2. 让提供者拥有自己的描述信息

名称、图标、支持的操作、格式能力等信息，尽量由对应功能的提供者声明，通用消费者负责展示和调用。

例如，笔记列表可以读取格式注册表里的显示信息，而不必维护“Markdown 用哪个图标、自由页面用哪个图标”的判断列表。这样新增格式时，改动主要留在新格式插件中。

当前列表与新建菜单读取格式的 `label`、`icon`；icon 使用 UI 服务支持的图标名称，例如 FileText、FileCode2。缺失格式、空图标或不支持的名称会回退到普通文件图标。新增格式无需再往列表中添加类型判断。

专门处理某种格式的编辑器可以判断该格式类型；不需要为了消除所有条件分支而引入额外注册系统。

## 3. 通过明确接口合作，保持依赖可见

包依赖与服务依赖含义不同：前者解决代码和类型来源，后者表达运行时需要的能力。开发内置插件时，在自己的包清单中分别声明；引用其他插件的公开类型，运行时通过 `ctx` 服务合作。

设计接口时，说明输入、输出、失败方式和资源归属，比只提供一个方法名更有用。前端与后端是不同运行环境，同名服务也可能有不同接口；跨端通信通过插件注册的 HTTP 路由，不把 Context 当作跨进程共享对象。

同步请求结果适合调用服务；多个插件关心某件事发生时适合事件；需要贡献编辑器、过滤器或界面入口时适合注册接口。优先复用已有机制，避免为每个小功能发明一套通信方式。

新增合理功能若很难通过已有接口实现，可以扩展接口，或明确记录双方的合作约定，不必为了形式上的解耦搭建一套庞大框架。

## 4. 界面和样式尽量由所属插件维护

业务插件拥有自己的视图和 CSS，布局插件提供挂载位置，UI 插件提供共享组件与 React 运行时。内置插件通过 `styles` 声明样式加载，通过自身 Tailwind 入口扫描自身视图；共享主题 token 是正常的公开依赖。

写 CSS 时，优先使用能识别所属组件的类名和根选择器，减少通用选择器意外影响其他界面的机会。使用根选择器不等于安全隔离，嵌套插件、弹出层和全局样式仍需要实际检查。

尽量避免通过别人内部的类名、元素 ID 或 HTML 层级调整布局。如果编辑器需要更宽的标题区域，可以考虑由编辑区外壳提供布局选项，让外壳管理自己的 DOM。具体是否增加选项，应根据真实需求决定。

当前格式可声明 `editorLayout: 'wide'` 请求宽版标题区域；省略、standard 或运行时无法识别的值使用标准布局。Markdown 与自由页面已使用这个字段，具体 CSS 由 editor-host 拥有。旧 editorClass 字段保留兼容，但内置格式不再依靠它修改外壳样式。这是格式描述字段，并不是 editorHost.register 的新参数，也没有增加架构拦截规则。

主题、布局和某些编辑器确实可能需要全局样式、焦点或 DOM 操作。遇到这类需求，说明影响范围，并在停用时恢复自己修改的状态即可，不必为了统一形式强行封装所有 DOM 操作。

## 5. 数据位置与存储实现分开考虑

新内置插件可以用 `runtime.dataDir` 保存自己的持久数据。优先由数据的所有者提供读写接口，减少消费者推测对方的目录、文件名和保存格式。

例如，图片资源插件若通过笔记存储的文件路径推导图片目录，就会依赖“笔记保存在本地文件中”这一实现。未来替换为数据库存储时，这种约定可能需要一起调整。

当前图片插件仅依赖 http，新上传文件写入 runtime.dataDir，即 `<dataDir>/plugin-data/note-assets/`；不再读取 ctx.storage.file。读取依次尝试新目录、旧 file 兼容入口旁的 note-assets/（如有）、`<dataDir>/note-assets/`，不自动移动或删除旧文件。已有图片 URL 保持不变。备份时应包含新目录及仍在使用的旧目录；若以后撤掉自定义 file 兼容入口，应先显式保留或迁移其旧图片目录。

配置应用失败后的恢复，不会撤销已经发生的文件写入、命令或网络请求。涉及这些副作用时，应由插件明确处理失败和重试，不依赖配置系统替它撤销业务操作。

## 6. 资源跟随生命周期，保存发生在停止之前

使用现有的 `ctx.effect`、SDK 监听和挂载接口登记清理动作，或在自行管理资源时提供对应释放逻辑。注意计时器、DOM、订阅、弹出层、请求与后台任务，尤其是重复启停后是否残留。

需要保存草稿或等待业务操作时，参与 `plugins/before-stop` 准备流程；释放阶段主要负责清理。准备流程不能阻止其他标签页、进程退出或异常故障，重要的未保存内容仍需要自己的恢复策略。

依赖服务可能暂时缺失。尽量让插件进入可理解的等待或不可用状态，并在服务恢复后重新工作。对未知或暂时没有提供者的数据，优先保留，避免误当成默认格式覆盖。

## 7. 按改动风险验证，不为自包含增加仪式

通常先验证本次改动影响的场景，再运行项目要求的检查。涉及界面时，还要实际观察页面；构建成功不能证明布局、焦点或交互正确。

可以根据改动选择这些检查：

- 新增提供者后，通用列表或菜单能否自动展示它的信息？
- 插件停用再启用后，界面、监听器和资源是否重复？
- 依赖暂时消失或被兼容实现替换后，消费者能否恢复？
- 浅色、深色、窄屏下，样式是否影响其他插件？
- 使用旧数据启动后，内容、图片和设置是否仍可读取？
- 导出的运行包是否包含需要的资源，公开资源是否声明完整？

跨插件的集成测试可以保留在根测试目录。单插件独立构建、隔离验收、服务契约版本和通用数据迁移框架，目前不作为新增插件的前置要求；等独立发布或升级需求明确后再考虑。

## 8. 交接时记录必要信息

插件的清单与公开类型是第一手接口信息。复杂插件可在自己的 README 中简要说明：负责什么、依赖什么、提供什么、数据放哪里、启停会发生什么，以及必要的验证方法。

如果有跨插件样式约定、旧路径兼容或必须操作全局状态的特殊需求，记录原因和影响方即可。文档的目的，是让下一位作者理解设计和取舍，而不是增加一套限制插件表达能力的规则。
